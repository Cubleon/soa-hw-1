# Архитектура маркетплейса

Учебный проект: [C4-диаграмма](architecture/container.svg), обоснование архитектуры и один сервис в Docker.

**Реализован только каркас Orders:** HTTP-сервер на Python с `GET /health`, возвращающим `200 OK` и `{"status":"ok"}`. Бизнес-логики, доменных API, баз данных и интеграций в коде нет. Остальные сервисы и взаимодействия описывают целевую архитектуру.

## 1. Запуск и проверка

Собрать образ и запустить сервис из корня проекта, дождавшись успешного health-check:

```sh
docker compose up --build --wait --wait-timeout 60
```

Проверить состояние контейнера — ожидается `healthy`:

```sh
docker compose ps
```

Проверить сервер через опубликованный порт с помощью `curl` — ожидаются `200 OK` и `{"status":"ok"}`:

```sh
curl --fail --show-error --include --max-time 5 http://localhost:8080/health
```

## 2. Домены, сервисы и владение данными

### Домены и зоны ответственности

| Домен | Описание зоны ответственности |
| --- | --- |
| <a id="domain-users"></a>Пользователи | Регистрация, вход, роли покупателя и продавца, профиль, контакты и выбранные категории. Один аккаунт может иметь обе роли. |
| <a id="domain-catalog"></a>Каталог и доступность | Управление товарами продавцов, категориями, ценами, остатками и резервами. Проверка принадлежности товара продавцу и предотвращение продажи сверх остатка. |
| <a id="domain-feed"></a>Персонализированная выдача | Формирование ленты опубликованных доступных товаров: сначала выбранные категории, затем остальные; внутри групп — по новизне. Гостям и пользователям без предпочтений — общая лента по новизне. |
| <a id="domain-orders"></a>Заказы | Оформление заказа, фиксация состава и стоимости по подтверждённым ценам, управление статусами и согласование резервов с каталогом. |
| <a id="domain-billing"></a>Расчёты и платежи | Расчёт суммы платежа по снимку заказа, комиссии и долей продавцов; проведение и учёт оплат и возвратов через внешнего провайдера. |
| <a id="domain-notifications"></a>Уведомления | Отправка email/SMS об изменении статуса заказа, выбор канала, учёт результатов доставки и повторных попыток. |

### Распределение доменов по сервисам

| Домен | Сервис | Обоснование размещения |
| --- | --- | --- |
| Пользователи | [Users](#service-users) | Зона [управления аккаунтами](#domain-users) реализуется функциями регистрации, входа и ведения профиля Users. Общая идентичность двух ролей позволяет избежать дублирования аккаунтов. |
| Каталог и доступность | [Catalog](#service-catalog) | Зона [управления ассортиментом и доступностью](#domain-catalog) требует совместной проверки цены и остатка. Catalog объединяет редактирование товаров и атомарное резервирование в одной БД. |
| Персонализированная выдача | [Feed](#service-feed) | Зона [формирования персональной ленты](#domain-feed) реализуется ранжированием собственных проекций товаров и предпочтений. Feed можно масштабировать отдельно от операций изменения каталога. |
| Заказы | [Orders](#service-orders) | Зона [оформления и сопровождения заказа](#domain-orders) соответствует функциям фиксации снимка покупки и управления её статусами. Orders сохраняет историю независимо от изменений карточек товаров. |
| Расчёты и платежи | [Billing](#service-billing) | Зона [платёжных расчётов и учёта](#domain-billing) требует обработки внешнего платёжного протокола и повторных callback. Billing объединяет расчёт платежа и запись финансового результата, не меняя данные заказа напрямую. |
| Уведомления | [Notifications](#service-notifications) | Зона [доставки сообщений](#domain-notifications) реализуется отдельной очередью заданий, отправкой и повторами. Сбой email/SMS-провайдера не должен блокировать оформление и оплату заказа. |

### Владение данными и ответственность сервисов

| Сервис | Какими данными владеет | За что отвечает |
| --- | --- | --- |
| <a id="service-users"></a>Users | **Users DB**, отдельная PostgreSQL БД, доступ только Users: аккаунты, хеши паролей, роли, профили, контакты, выбранные категории. | Регистрация и аутентификация; управление профилем и ролями; публикация изменений предпочтений. Источник истины об аккаунтах. |
| <a id="service-catalog"></a>Catalog | **Catalog DB**, отдельная PostgreSQL БД, доступ только Catalog: товары, категории, `seller_id`, актуальные цены, остатки, резервы. | Редактирование своего каталога продавцом; проверка цен и доступности; атомарное резервирование, списание и освобождение остатков; публикация изменений товаров. |
| <a id="service-feed"></a>Feed | **Feed DB**, отдельная PostgreSQL БД, доступ только Feed: проекции товаров и предпочтений для ранжирования. Источники исходных данных — Catalog и Users. | Построение и выдача персональной ленты; обновление и восстановление проекций через события и API владельцев. Не изменяет оригинальные цены, остатки или профиль. |
| <a id="service-orders"></a>Orders | **Orders DB**, отдельная PostgreSQL БД, доступ только Orders: заказы, снимки названий, продавцов и цен, суммы, контакты/адрес заказа, история статусов, ключи идемпотентности. | Оформление и чтение заказа; расчёт итога товаров по подтверждённым ценам; управление жизненным циклом; резервирование через Catalog; применение финансовых результатов и публикация статусов. |
| <a id="service-billing"></a>Billing | **Billing DB**, отдельная PostgreSQL БД, доступ только Billing: суммы платежей, снимки комиссий и долей продавцов, попытки оплаты, provider ID, журнал операций, возвраты. Карточные реквизиты не хранятся. | Расчёт суммы к оплате по неизменяемому снимку заказа; взаимодействие с провайдером; проверка callback; учёт оплат и возвратов; публикация результатов. Комиссия удерживается из доли продавца. |
| <a id="service-notifications"></a>Notifications | **Notifications DB**, отдельная PostgreSQL БД, доступ только Notifications: шаблоны, задания, каналы, попытки, delivery ID, результаты и ключи дедупликации. | Получение событий статуса; запрос контактов через Users API; отправка email/SMS; обработка ошибок и повторов. Не владеет исходными контактами пользователей. |
| Web App | Собственной доменной БД нет. | Пользовательский интерфейс ленты, каталога, профиля и заказа; вызовы API через Gateway. |
| API Gateway | Собственной доменной БД нет. | Маршрутизация клиентских запросов и webhook; доменные права на ресурс проверяются сервисом-владельцем. |
| Event Broker | RabbitMQ хранит очереди сообщений, повторы и DLQ; доменной БД нет. | Асинхронная доставка событий подписчикам. Источниками истины остаются БД владельцев; outbox и сведения об обработке событий каждый сервис хранит в своей БД. |

## 3. Взаимодействия

### Синхронные запросы

| Инициатор → получатель | Что передаётся / зачем | Способ |
| --- | --- | --- |
| Покупатель / продавец → Web App | Работа с интерфейсом | HTTPS |
| Web App → Gateway → Users | Вход, профиль, предпочтения | HTTPS / JSON |
| Web App → Gateway → Catalog | Чтение карточки, изменение своего каталога | HTTPS / JSON |
| Web App → Gateway → Feed | Получение ленты | HTTPS / JSON |
| Web App → Gateway → Orders | Оформление и получение состояния заказа | HTTPS / JSON |
| Web App → Gateway → Billing | Получение статуса платежа и ссылки на оплату своего заказа | HTTPS / JSON |
| Orders → Catalog | Проверка текущих цен; резервирование, подтверждение или освобождение остатков | HTTPS / JSON, идемпотентные команды по `order_id` |
| Feed → Catalog / Users | Экспорт снимков товаров / предпочтений для начального заполнения и восстановления проекций | HTTPS / JSON, служебный доступ |
| Billing → платёжный провайдер | Создание платежа / возврата, сверка результата | HTTPS / JSON, ключ идемпотентности |
| Покупатель → платёжный провайдер | Ввод платёжных данных на странице провайдера | HTTPS |
| Notifications → Users | Актуальный контакт и разрешённый канал доставки | HTTPS / JSON |
| Notifications → email/SMS провайдер | Отправка сообщения | HTTPS / JSON |
| Каждый сервис → только своя БД | Работа с собственным состоянием | SQL / TLS |

На сетевых вызовах проектируются таймауты. Изменяющий запрос повторяется только с тем же ключом идемпотентности. Недоступность Catalog временно мешает новому заказу; недоступность Feed не мешает чтению карточки через Catalog. Сервисы проверяют JWT Users по публичному ключу из конфигурации и права на ресурс; распределение и ротация ключей относятся к эксплуатации. Межсервисные обращения используют отдельные служебные полномочия.

### Асинхронные взаимодействия

Все перечисленные доменные события идут через RabbitMQ по AMQP / TLS. Каждому подписчику выделяется собственная очередь: событие заказа должно независимо попасть и в Billing, и в Notifications при соответствующих подписках.

| Издатель | Событие | Подписчик | Назначение |
| --- | --- | --- | --- |
| Users | `UserPreferencesUpdated` | Feed | Обновить копию предпочтений |
| Catalog | `ProductChanged`, `ProductRemoved` | Feed | Обновить / удалить карточку из проекции |
| Orders | `OrderPlaced` | Billing | Рассчитать платёж по подтверждённому снимку заказа и создать попытку |
| Orders | `OrderCancelled` | Billing | Отменить незавершённую оплату или инициировать возврат |
| Billing | `PaymentSucceeded`, `PaymentFailed`, `RefundSucceeded` | Orders | Изменить состояние заказа по финансовому результату |
| Orders | `OrderStatusChanged` | Notifications | Поставить уведомление о новом статусе в очередь |

Платёжный провайдер отдельно вызывает подписанный HTTPS webhook через Gateway в Billing. HTTP-обмен имеет ответ, но итог оплаты сообщается независимо от исходного запроса. Billing проверяет подпись, сумму, валюту, уникальность операции и сохраняет результат до подтверждения callback. Возврат браузера со страницы оплаты не доказывает факт оплаты.

## 4. Альтернативы и финальный выбор

**Статус решения:** принято для целевой учебной архитектуры.

### Контекст

Маркетплейс должен поддерживать пользователей двух ролей, каталог продавцов, персонализированную ленту, заказы, расчёт и учёт платежей, уведомления о статусах. Нагрузка, размер команды и SLA не заданы. На этапе задания разрешён только каркас одного сервиса с health-check; реализация доменных операций не требуется.

Ключевые различия доменов: каталог часто читается и меняется продавцами, история заказа должна сохраняться независимо от карточки товара, платёж зависит от внешней системы, уведомления могут доставляться с задержкой. Предпочтения категорий достаточны для начальной персонализации.

### Вариант A: модульный монолит

Один backend содержит модули Users, Catalog, Feed, Orders, Billing, Notifications. Модули общаются внутри процесса. Одна БД принадлежит одному приложению, таблицы сгруппированы в схемы модулей, доступ идёт через интерфейсы модулей. Frontend — отдельное приложение.

**Плюсы:** простой запуск и диагностика; один релиз; заказ и резерв можно согласовать локальной транзакцией; меньше инфраструктуры и межсетевых отказов. Практичный старт небольшой команды.

**Минусы:** единая единица масштабирования и отказа; новая платёжная интеграция требует релиза всего backend; нагрузка ленты конкурирует с оформлением заказов за ресурсы процесса и БД. Запрет межмодульного SQL необходимо поддерживать на ревью и проверками.

**Trade-off:** дешевле эксплуатация и проще транзакции в обмен на зависимость релизов, масштабирования и отказов разных доменов.

### Вариант B: шесть сервисов по доменным границам

Users, Catalog, Feed, Orders, Billing и Notifications — самостоятельные приложения с отдельными БД. Запросы, требующие немедленного результата, идут по HTTPS; распространение изменений и длительные процессы используют RabbitMQ. Web App обращается через API Gateway.

**Плюсы:** самостоятельные релизы; масштабирование Feed отдельно от Orders; отказ провайдера уведомлений не прерывает приём заказа; финансовые данные и протокол провайдера имеют одного владельца. Изменение карточки не переписывает снимок уже оформленного заказа.

**Минусы:** больше развёртываний, секретов, резервных копий и наблюдаемости; сетевые ошибки входят в штатные сценарии. Оформление заказа и оплата не атомарны между БД; нужны восстановление после сбоя, дедупликация и компенсации. Лента и статусы после событий обновляются с задержкой.

**Trade-off:** независимость доменов в обмен на стоимость распределённой системы. Брокер устраняет ожидание внешних побочных действий, но добавляет очереди, повторы и необходимость сопровождать контракты событий.

Варианты отличаются единицей развёртывания, границами транзакций и способом взаимодействия. Общая БД варианта A принадлежит единственному backend-приложению; для выбранного варианта B общих БД между сервисами нет.

### Решение

Для целевой архитектуры выбран **вариант B**. Он делает явными границы требуемых кейсом доменов и позволяет отдельно развивать выдачу, управление ассортиментом и платёжные интеграции. Обоснование основано на разных обязанностях и режиме отказов, а не на неподтверждённой нагрузке.

Цена выбранного варианта — распределённая согласованность и более дорогая эксплуатация. При запуске реального продукта небольшой командой без подтверждённой нагрузки вариант A мог бы быть экономичнее.
